# CRM 시안 생성 프로토타입 — 구조와 기술 선택 이유

## 1. 무엇을 만들었나

1~8주차에 만든 프롬프트(P1 POD·카피·이미지 연출, P2 이미지, P3 HTML)를 하나의 흐름으로 연결한 도구입니다.
각 단계에서 AI가 방향이 다른 3개 안을 만들고, 사람이 하나를 골라(필요하면 고쳐서) 다음 단계로 넘깁니다.

```
입력 (타겟 페르소나, 소구 강도(HOT/WARM/COLD), 이미 사용된 1순위 Pod, 제품명, 컬러, Pod별 스펙)
 ↓
① Pod 순서·레이아웃 3안   → 사람이 1개 선택
 ↓
② 카피 3안 (①을 전제로)   → 사람이 1개 선택, 헤드·바디 직접 수정 가능
 ↓
③ Pod마다 이미지 3안      → Pod별로 1개 선택, 마음에 안 드는 Pod만 다시 생성
 ↓
④ 최종 CRM HTML 조립 → 미리보기 (+ P1 [8] 형식의 html_input.json)
```

## 2. 구조 설계에서 한 결정

### 원본 프롬프트를 단계별로 나눴다
P1은 POD 순서, 카피, 이미지 연출을 한 번에 출력합니다. 과제는 "POD를 고른 뒤 카피"이므로 P1을 ①②③ 세 프롬프트로 나눴고,
뒤 단계는 앞 단계에서 **사람이 고른 결과**를 입력으로 받습니다. 한 번에 적게 시킬수록 규칙도 더 잘 지킵니다.
원본은 `backend/app/prompts/original/`에 그대로 보관했습니다.

### 안 3개는 한 번에 받지 않고, 방향을 달리해 3번 병렬로 호출한다
한 호출에서 여러 안을 쓰게 하면 안끼리 비슷해지고 형식이 무너지기 쉽습니다.
안마다 방향(예: "기능·수치를 앞세우는 카피", "사용 장면을 그리는 카피", "효익을 짧게 정리하는 카피")을 줘서 사람이 실제로 비교할 거리가 있게 했습니다.

### 앞 단계가 바뀌면 뒤 단계는 초기화한다
Pod 순서를 바꾸면 그 순서로 쓴 카피와 이미지는 전제가 깨집니다. 다시 생성하거나 다른 안을 고르면 뒤 단계를 비우고,
앞 단계를 고르지 않으면 다음 단계를 생성할 수 없게(API 400) 했습니다.

### 규칙 검사는 코드로 한다 (P1의 [7] 자가 점검 대체)
모델에게 "스스로 점검하라"고 하면 점검했다고 말할 뿐 실제로 지키지는 않는 경우가 많았습니다. 그래서 확인 가능한 규칙은 코드가 검사합니다.
- **코드가 직접 맞추는 값**: eyebrow(=Pod명), 레이아웃별 화면비, L3 외 Safe Zone
- **경고로 보여주는 위반**: 헤드카피 20자·바디카피 110자 초과, 헤드카피 유형 4종 미만·중복, 어미 배열 중복, 1순위 Pod 중복, 이동한 Pod 3개 미만, 레이아웃 연속·종류 부족, 컬러 라인업 밖 색, L3 Safe Zone 금지어
- **팩트체크 대조**: 카피가 근거로 든 구절이 그 Pod의 입력 스펙에 실제로 있는지 원문과 비교
- **헤드카피 길이 보정**: 모델은 글자 수를 정확히 세지 못해 20자를 자주 넘깁니다. 코드가 길이를 세어 넘긴 헤드카피만 모델에게 다시 줄이게 합니다.

경고는 카드에 그대로 보여주고, 최종 판단은 사람이 합니다. 사람이 고친 내용도 저장할 때 같은 규칙으로 다시 검사합니다.

### 최종 HTML은 LLM이 아니라 템플릿으로 조립한다
P3의 디자인 토큰과 L1~L5 레이아웃 정의는 이미 확정된 규칙입니다. 이걸 모델이 매번 HTML로 쓰게 하면 레이아웃이 깨질 수 있어,
Jinja2 템플릿으로 옮겨 결정적으로 조립했습니다. **"생성은 AI, 조립은 코드"**가 이 프로토타입의 기본 원칙입니다.

### 이미지에는 글자를 넣지 않는다
카피는 HTML에서 텍스트로 얹습니다. 이미지 모델이 한글을 그리면 오타가 나고 수정도 어렵기 때문입니다.
이미지 생성에는 P2 원문을 그대로 쓰고, ③에서 모델이 쓴 Pod별 이미지 Input Data를 뒤에 붙여 보냅니다. 공식 제품 사진은 참조 이미지로 함께 보냅니다.

### 호출 폭주는 서버에서 막는다
버튼 잠금은 화면 안에서만 동작해서 새로고침, 다른 탭, 스크립트에는 효과가 없습니다. 그래서 서버에 세 겹의 상한을 두었습니다.
- 한 실행에서는 생성을 한 번에 하나만 합니다(409). 동시에 두 개가 돌면 호출이 두 배가 되고 저장 파일도 서로 덮어쓰기 때문입니다.
- 생성 요청은 1분에 10회까지만 받습니다(429). 반복 호출 버그나 루프를 끊기 위한 상한입니다.
- Vertex 이미지 호출은 하루 100장까지입니다(재시도 포함). 생성 전에 필요한 장 수를 먼저 계산해서, 한도를 넘으면 호출 없이 거절합니다.

## 3. 기술 스택과 선택 이유

| 구분 | 선택 | 이유 |
|---|---|---|
| 프론트 | React + Vite + TypeScript, pnpm | 단계마다 "카드 N개 → 선택 → 수정"이 반복되므로 컴포넌트 하나(`StepPanel`)로 재사용. 백엔드 상태를 타입으로 맞춤 |
| 스타일 | Tailwind CSS v4 | 빌드 시 CSS가 만들어져 런타임 비용이 없고, 프로토타입을 빠르게 만들기 좋음 |
| 백엔드 | FastAPI + uv | 단계별 API(`generate` / `select`)로 흐름이 코드에 그대로 드러남. `/docs`로 화면 없이도 검증 가능 |
| LLM 연결 | LangChain | 프롬프트 템플릿과 구조화 출력(`with_structured_output`)을 모델과 상관없이 같은 코드로 씀. 모델 교체는 `.env`만 바꿈 |
| 텍스트 모델 | Vertex AI Gemini (`gemini-3.5-flash`) | 회사 보안 정책상 외부 LLM API는 쓸 수 없고, 회사 GCP 프로젝트 안의 Vertex AI는 허용됨. API 키 없이 회사 계정(ADC)으로 인증 |
| 이미지 모델 | Vertex AI Gemini 이미지 (`gemini-3.1-flash-image`) | 같은 회사 프로젝트 안에서 사용 가능. P2가 전제한 대로 제품 사진을 참조 이미지로 함께 보낼 수 있음. 후보 3개를 같은 조건으로 비교해 골랐다(아래) |
| HTML 조립 | Jinja2 | 위 "조립은 코드" 원칙 |
| 저장 | JSON 파일 + 이미지 폴더 | 배포가 필요 없는 과제. 실행 하나가 폴더 하나라 단계별 기록을 그대로 확인 가능 |

### 모델을 정하기까지
처음에는 오픈 모델(Qwen3-8B)을 회사 GCP에서 직접 서빙하려 했습니다. 그런데 배정된 환경이 GPU 없는 Colab Enterprise(4 vCPU / 16GB)라서
8B 모델도 시연 속도로 돌릴 수 없었습니다. 회사에 확인한 결과 프로젝트 안의 Vertex AI Gemini를 쓸 수 있어 텍스트와 이미지 모두 Vertex로 바꿨습니다.
오픈 모델 경로(OpenAI 호환 서버: Ollama, vLLM)는 `LLM_PROVIDER=openai`로 그대로 남겨 두었습니다.

### 이미지 모델 비교
프로젝트에서 호출되는 이미지 모델 3개에 같은 연출안·같은 공식 제품 사진을 넣어 카메라 Pod 이미지를 만들어 비교했습니다.
이 과제에서 가장 중요한 기준은 **제품 형태(렌즈 수, 색)를 정확히 재현하는가**입니다.

| 모델 | 1장 시간 | 결과 |
|---|---|---|
| `gemini-2.5-flash-image` (처음 사용) | — | 제품이 작고 디테일이 흐림 |
| **`gemini-3.1-flash-image` (채택)** | 약 11초 | 제품이 크고 선명함. 렌즈 2개 + 플래시, 라벤더 색 정확 |
| `gemini-3-pro-image` | 약 61초 | 사진 품질은 가장 높지만 렌즈 3개·이전 세대 디자인으로 제품 재현이 틀림. 15장 생성 시 15분 이상 |

텍스트도 같은 방식으로 비교했습니다. `gemini-3.1-pro-preview`는 카피 규칙 경고가 적었지만(3안 합계 6개 → 1개) 약 6배 느렸고,
flash의 생각 수준을 올리면 pro보다 느리면서 경고는 줄지 않았습니다. 시연 속도를 우선해 `gemini-3.5-flash`(생각 수준 low)를 유지했습니다.
모델은 `.env`의 `VERTEX_TEXT_MODEL` / `VERTEX_IMAGE_MODEL`만 바꾸면 교체됩니다.

## 4. 운영하며 고친 것 (실측)

| 문제 | 대응 |
|---|---|
| 15건을 동시에 호출하자 일부 요청이 50분 넘게 응답 없이 멈춤 | 요청마다 45초 제한을 걸고, 실패한 안만 한 번 더 시도. 동시 요청은 6건으로 제한 |
| 호출 1건이 약 12초 | 생각 수준을 `low`로 낮춰 약 3초. 결과 ① 약 7초, ② 약 12초, ③ 연출안 15건 약 15초 |
| 스펙에 없는 효익("발열 걱정 없이")을 쓰는 안 | 프롬프트에서 스펙 밖 주장을 금지하고, 팩트체크 근거를 원문과 대조 |
| 헤드카피 20자 초과가 잦음 | 코드가 길이를 세고, 넘긴 것만 다시 줄이게 하는 보정 호출 |
| 이미지 모델이 간헐적으로 429(용량 부족) | 한 장씩 보내고, 429면 기다렸다 다시 시도. 3안 중 일부만 성공해도 성공한 안을 보여줌 |
| 새 이미지 모델이 수 분간 계속 429 (쿼터·용량 소진) | 기다렸다 다시 보내도 429면 이전 모델(`gemini-2.5-flash-image`)로 대신 생성하고, 10분간은 새 모델을 건너뜀. 지금 쓰는 모델은 `/api/health`에 표시 |
| 시연 중 이미지 생성이 실패할 위험 | 잘 나온 이미지를 Pod·화면비별 풀에 저장해 두고 `IMAGE_PROVIDER=pool`로 즉시 전환 |

## 5. 한계와 사람이 맡는 부분

- 근거 목록에 적지 않은 주장, 바디 첫 문장 구조, 타겟 유형별 금지 어휘는 코드로 완전히 잡지 못합니다. 사람이 카드에서 보고 고릅니다.
- ③은 Pod별로 따로 만들기 때문에 "5개 Pod 전체에서 연출을 섞는다"는 P1 규칙은 자동으로 보장되지 않습니다. 안마다 연출 방향(제품 단독 / 손·인물 / 배경)을 다르게 줘서 사람이 고를 때 섞도록 했습니다.
- 이미지의 기기 형태(렌즈 수, 비율)가 실제와 다를 수 있어 제품 사진을 참조로 붙이고, 최종 선택은 사람이 합니다.

이 한계들이 바로 "AI가 안을 만들고 사람이 고르는" 구조를 택한 이유입니다.
